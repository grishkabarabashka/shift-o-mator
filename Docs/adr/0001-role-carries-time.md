# ADR-0001. Роль несёт своё время

**Статус:** принято

## Контекст

В текущем Excel код смены (`SL`, `BATCH LATE`) не несёт информации о времени. Знание
«какой код какое окно означает» существует только в головах планировщиков. Новый человек
не может планировать без наставника, а ответить на вопрос «кто сейчас на смене» без
пересчёта в уме невозможно.

## Решение

`ShiftRole` хранит `timeZone`, `start`, `end`, `crossesMidnight`. Окно задано в
фиксированной таймзоне роли, а не в таймзоне человека и не в UTC-смещении.

Shift lead в Americas — это нью-йоркское окно, потому что передача между регионами
происходит в конкретное время. Человек из Пуны, назначенный на эту роль, работает по
нью-йоркскому окну; для него это ночная смена, и система считает это сама.

Переопределение возможно на двух уровнях: персональном (у этого человека эта роль всегда
на час позже) и разовом (в конкретный день). Оба видимо помечаются в интерфейсе.

## Следствия

- Назначение человека на роль полностью определяет интервал смены — расчёт покрытия
  и timeline становятся тривиальными.
- Хранение окна как локального времени в именованной таймзоне даёт корректное поведение
  на переходах DST: при переходе США на летнее время смена человека из Пуны сдвигается
  автоматически.
- Дата назначения трактуется в таймзоне роли — это устраняет неоднозначность для смен,
  пересекающих полночь.
- Требуется дисциплина работы с датами: см. [ADR-0002](0002-location-is-calendar-only.md)
  и раздел [02-time.md](../02-time.md).

## Альтернативы

- **Окно в UTC-смещении.** Ломается дважды в год на переходах DST.
- **Окно по локальному времени человека.** Убивает смысл передачи смены: два человека
  на одной роли из разных локаций работали бы в разное время. Кажется нужным для service
  transition, но там задача решается набором ролей `ST_AMER` / `ST_EMEA` / `ST_APAC`,
  у каждой своё окно — одна ветка вместо двух.
