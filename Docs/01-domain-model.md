# Доменная модель

## Схема

```
Location ──────┐
               ├──> Person ──> RoleEligibility ──┐
PlanningUnit ──┤                                 ├──> Assignment
               └──> ShiftRole ───────────────────┘         │
               │                                            ├──> CompDayEntry
               ├──> CoverageRule ──────> CoverageCell       │
               ├──> AbsenceCapacityRule                     │
               └──> CompDayPolicy                    Absence ┘
```

## Planning unit

То, что в разговоре называется «регион», в модели — **единица планирования**. Это
организационная и планировочная граница, а не географическая
(см. [ADR-0003](adr/0003-planning-unit-not-geography.md)).

- Americas включает Нью-Йорк, Чикаго и **Пуну** — люди из Индии закрывают смены Америк.
- Service transition — отдельная единица, люди в ней разбросаны по всем регионам,
  планирует их один человек сразу за все локации.

Атрибуты: название, планировщики (кто вправе редактировать), политика comp days, набор
ролей, правила покрытия, лимиты отсутствий.

В интерфейсе слово «регион» можно оставить — оно привычно. В коде `PlanningUnit`, чтобы
добавление пятой единицы («Automation», «ST Global») не ломало модель.

## Location

Локация отвечает **только за две вещи** ([ADR-0002](adr/0002-location-is-calendar-only.md)):

1. календарь выходных и государственных праздников (какой день считается для человека
   нерабочим);
2. таймзону для отображения графика этому человеку в его времени.

**Ко времени смены локация отношения не имеет.** Это ключевое разделение, на котором
ломаются наивные модели.

Атрибуты: название, таймзона, ключ календаря праздников (`US`, `GB`, `CH`, `SG`, `IN`),
дни недели, считающиеся выходными.

## Shift role

**Роль несёт своё время** ([ADR-0001](adr/0001-role-carries-time.md)). Это центральное
решение и прямой ответ на главную проблему текущего Excel — необходимость помнить, какой
код какое время означает.

```
ShiftRole {
  unitId
  code            'SL', 'BATCH', 'BATCH_LATE', 'CAVA', 'ST_AMER'
  label, color
  timeZone        таймзона, в которой задано окно
  start, end      '07:00' – '15:00'
  crossesMidnight
  editableTime      можно ли править время в конкретной ячейке
  countsAsCoverage  участвует ли роль в расчёте покрытия
}
```

Правила:

- **Роли принадлежат единице планирования** ([ADR-0004](adr/0004-roles-belong-to-unit.md)).
  Глобального справочника ролей нет: `AMER/SL` и `EMEA/SL` — разные сущности с разным
  временем, разными людьми и разными требованиями покрытия. Совпадение кодов между
  юнитами нормально.
- **Окно всегда задано в фиксированной таймзоне роли.** Shift lead в Americas — это
  нью-йоркское окно, потому что передача между регионами происходит в конкретное время.
  Человек из Пуны, назначенный на эту роль, работает по нью-йоркскому окну — для него это
  ночная смена, и система считает это сама.
- Привязки «по локальному времени человека» в модели нет. Она кажется нужной для service
  transition, но там задача решается набором ролей `ST_AMER`, `ST_EMEA`, `ST_APAC`,
  у каждой своё окно. Одна ветка вместо двух.
- Переопределение времени возможно на двух уровнях: **персональном** (у этого человека
  эта роль всегда на час позже) и **разовом** (в конкретный день). Оба видимо помечаются
  в интерфейсе.

Правило одной фразой: **роль задаёт, когда работать; локация задаёт, когда работа
считается выпавшей на выходной.**

## Person

```
Person {
  displayName, employeeId
  unitId, locationId
  isPlannerOnly              менеджеры: в сетке планирования не участвуют
  eligibility[]              доступные роли с целевыми долями и лимитами
  availableWeekdays[]
  constraints                отдых, подряд, выходные
  preferences
  calendarToken              для ICS-подписки
}
```

**Отдельной сущности «рабочий паттерн» нет**
([ADR-0005](adr/0005-no-work-pattern-entity.md)). Участие в ротации полностью
определяется набором доступных ролей и днями доступности:

- инженер service transition: единственная доступная роль `ST_EMEA`, дни Пн–Пт.
  В ротацию поддержки физически не попадёт;
- менеджер: пустой набор ролей плюс `isPlannerOnly`, в сетке не появляется;
- обычный инженер: несколько ролей с целевыми долями.

**Целевые доли вместо булевых флагов**
([ADR-0006](adr/0006-eligibility-target-shares.md)). Eligibility хранит не «умеет / не
умеет», а желаемое распределение:

```
{ roleId: SL,    targetShare: 0.4, minPerWeek: 2, maxPerWeek: 6 }
{ roleId: BATCH, targetShare: 0.2 }
{ roleId: CAVA,  targetShare: 0.4 }
```

Это решает случай «этому человеку нужно давать эту роль чаще остальных» без исключений
в коде. Справедливость тогда считается не как равенство, а как **отклонение фактической
доли от целевой**: человек с целью 0.4 по shift lead и фактом 0.15 — перекос, даже если
по абсолютным числам он в середине команды.

## Assignment

Назначение человека на роль в конкретную дату. Хранит источник (`MANUAL`, `GENERATED`,
`PATTERN`), возможное переопределение времени, автора и время создания.

Дата назначения — локальная дата смены **по таймзоне роли**. Это устраняет
неоднозначность для ночных смен, пересекающих полночь.

## Absence

Отсутствие: отпуск, comp day, обучение, больничный. Диапазон дат включительно.

Служебные поля, без которых импорт станет источником недоверия:

- `source: IMPORT | MANUAL` — ручные записи импорт никогда не перетирает;
- `importBatchId`, `lastSeenInImportAt` — для обнаружения исчезнувших записей;
- `syncedToHrAt` — занесено ли обратно в корпоративную систему.

## Comp day

Отгул за работу в выходной или праздник. **Это не событие в расписании, а начисление
с балансом** ([ADR-0007](adr/0007-comp-day-as-balance.md)) — сущность, которую легко
пропустить при проектировании и которая потом всплывает как источник расхождений.

```
CompDayPolicy {
  rules: [
    { workedOn: SATURDAY, defaultOffsetDays: -2 }   четверг той же недели
    { workedOn: SUNDAY,   defaultOffsetDays: +2 }   вторник следующей недели
    { workedOn: HOLIDAY,  defaultOffsetDays: +3 }
  ]
  expiryWeeks: 12
}

CompDayEntry {
  personId
  earnedForAssignmentId, earnedForDate
  proposedDate           из политики
  actualDate             после переноса планировщиком
  status: PROPOSED | SCHEDULED | TAKEN | EXPIRED | DECLINED
  expiresOn, syncedToHrAt
}
```

Механика:

1. Планировщик ставит человека на субботу. Система проверяет календарь **локации этого
   человека** — суббота нерабочая, значит порождается `CompDayEntry` со статусом
   `PROPOSED` и датой из политики.
2. В графике сразу появляется предварительная отметка отгула — светлым, пунктиром.
   **Планировщик видит последствие своего назначения в тот же момент, а не через неделю.**
3. Дефолтный день переносится перетаскиванием — на практике его двигают почти всегда.
   Статус меняется на `SCHEDULED`, отклонение от дефолта фиксируется.
4. Подтверждённый comp day блокирует назначение и участвует в проверке покрытия наравне
   с отпуском.
5. Незапланированные отгулы висят в балансе человека. Накопленные 6 неотгуленных дней —
   управленческий сигнал, который сейчас не виден нигде.

**Начисление — предложение, а не факт.** Планировщик подтверждает. Иначе ошибка
в календаре праздников тихо испортит баланс, а это уже деньги и отношения с людьми.

## Coverage rule

Требование минимального покрытия — то, чего нет ни в одной существующей системе и что
даёт наибольшую отдачу.

```
CoverageRule {
  unitId, roleId
  appliesTo: WEEKDAY | WEEKEND | HOLIDAY | DATE
  date, label      только для DATE: 'DR test', 'Month end'
  min              жёсткое требование
  target           желательное
  max              чтобы не переливать людей
}
```

Правила на конкретную дату перекрывают общие. **Это и есть механизм для событий**
([ADR-0008](adr/0008-events-are-dated-coverage-rules.md)) — DR-тест или закрытие месяца
описываются как набор правил с датой и меткой, а не отдельной сущностью «мероприятие».

## Absence capacity rule

Лимит одновременно отсутствующих. Действует не при планировании смен, а раньше — при
согласовании отпусков.

```
AbsenceCapacityRule {
  unitId
  scope: UNIT | ROLE_POOL(roleId)
  durationBucket: SHORT | LONG
  longThresholdWorkdays: 5
  maxConcurrent
  countsTypes: [VACATION, COMP_DAY, TRAINING]
}
```

Текущие правила команды как дефолты: не более 3 в длительном отсутствии, не более 4
в коротком.

**Ограничение по пулу ролей важнее общего**
([ADR-0010](adr/0010-absence-limits-by-role-pool.md)). Три человека в отпуске — не
проблема. Трое из четырёх, кто умеет быть shift lead, — проблема, и обычная система
отпусков её не увидит никогда. Именно это правило даст самую большую практическую отдачу.
