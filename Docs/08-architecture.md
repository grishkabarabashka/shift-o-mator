# Технические решения

## Стек

| Слой | Решение | Обоснование |
|---|---|---|
| Фронтенд | React + Vite + TypeScript (strict) | в периметре есть корпоративная библиотека компонентов на React |
| Состояние черновика | Zustand, правки списком патчей | undo/redo получается почти бесплатно |
| Серверное состояние | TanStack Query, отдельно от клиентского | не смешивать «данные с сервера» и «мои несохранённые правки» — главный источник багов в редакторах |
| Даты | Luxon | одна библиотека на весь проект |
| Шкала времени | d3-scale | только шкала, не готовый Gantt |
| Примитивы UI | Radix UI | поведение и доступность без навязанного вида |
| Тесты | Vitest | движок покрывается тестами с первого дня |
| Бэкенд | .NET, деплой в AKS | стандарт организации |
| Хранилище | Postgres | интервальные типы и exclusion constraints помогают с проверкой пересечений смен |
| Solver | на бэке | JS-реализация локального поиска будет медленной и непереносимой |

В MVP бэкенда нет: репозиторий in-memory поверх фикстур, персист в IndexedDB, импорт
и экспорт JSON.

## Визуальный слой

MVP собирается вне периметра, прод — на корпоративной библиотеке. Значит, критерий
выбора не красота, а **стоимость последующей замены оболочки**
([ADR-0013](adr/0013-headless-ui-layer.md)).

Отсюда headless-подход: Radix UI primitives плюс собственные стили. Radix даёт поведение,
доступность, фокус-менеджмент; внешний вид полностью свой. При переезде меняется слой
представления, логика остаётся.

Material UI и Ant Design отпадают: они навязывают собственную визуальную систему и модель
тем, переезд с них означает переписывание.

**Дизайн-направление:** плотная операционная консоль, а не дашборд. Нейтральная холодная
база, один акцент на активном состоянии, моноширинный шрифт для кодов ролей и времени,
нулевая декоративность. Красный и янтарный не используются нигде, кроме нарушений
покрытия, — чтобы дыры в графике были видны боковым зрением.

## Сетка

AG Grid Community не содержит range selection, fill handle и операций с буфером — то есть
именно тех функций, ради которых его берут. При 80 строках и ~30 колонках **собственная
реализация выигрывает** ([ADR-0014](adr/0014-own-grid-and-timeline.md)): полный контроль
над клавиатурой и paint-режимом, отсутствие лицензии, примерно 500–800 строк кода.
Решение окончательно подтверждается после просмотра реального Excel — станет видно, какие
операции действительно нужны.

## Масштаб

80 человек, 3–4 единицы. Это очень мало, и из этого следует:

- весь квартал (80 × 90 ≈ 7 200 назначений, ~1 МБ JSON) грузится в браузер целиком, одним
  запросом;
- никакой серверной пагинации, никакой ленивой подгрузки при скролле по времени;
- виртуализация в timeline не нужна вообще;
- solver на месяц считается за доли секунды, можно позволить перегенерацию с мгновенным
  превью при изменении весов.

Это стоит фиксировать явно, иначе команда по привычке начнёт строить под 10 000
пользователей и потеряет ту скорость реакции интерфейса, ради которой всё затевается.

## Граница данных

`ScheduleRepository` — единственная точка доступа к данным
([ADR-0012](adr/0012-schedule-repository-boundary.md)). В MVP реализация in-memory поверх
фикстур с персистом в IndexedDB и импортом/экспортом JSON. Позже та же сигнатура ложится
на .NET-эндпоинты без переделки интерфейса.

**Все методы асинхронные с самого начала**, даже когда данные локальные. Иначе потом
всплывут все места, где код неявно рассчитывал на синхронность.

Генератор — за таким же интерфейсом: в MVP простой жадный на клиенте (чтобы проверить UX
превью и объяснений), потом solver на бэке.

## Структура каталогов

```
src/
  domain/     типы и фикстуры — никаких зависимостей, кроме luxon
  engine/     чистые функции: dates, coverage, compDays, validate
  data/       ScheduleRepository и реализации
  store/      Zustand: черновик, патчи, undo/redo, блокировка
  features/   экраны и их компоненты
  ui/         примитивы поверх Radix и общие стили
```

Направление зависимостей строго вниз: `features` знает про `store` и `engine`, `engine`
знает только про `domain`, `domain` не знает ни про что.
